# Conference Readiness Map

## Purpose

Work backwards from a presentation date to define what evidence, artifacts, approvals, narrative, and boundaries must exist.

This skill is useful when a partner mentions a future conference, presentation, summit, symposium, or public milestone.

## Core principle

A conference presentation is not proof of success. It is a forcing function for disciplined preparation.

## Required inputs

Useful inputs:
- Target event or approximate date.
- Audience.
- Project status.
- Partner expectations.
- Available evidence.
- Institutional sensitivities.
- Claims the team wants to make.

If the conference is not confirmed, build two tracks:
- Confirmed-event track.
- Opportunity-readiness track.

## Method

1. Identify event ambiguity.
   - Is the event named?
   - Is date confirmed?
   - Is the presentation slot confirmed?
   - Is the audience clinical, technical, academic, executive, patient/community, or mixed?

2. Define presentation purpose.
   Choose one:
   - Announce collaboration.
   - Present early feasibility.
   - Present patient-centered rationale.
   - Present technical validation.
   - Recruit partners.
   - Build institutional support.
   - Share implementation framework.

3. Work backwards.
   Define what must be ready:
   - 12 weeks before.
   - 8 weeks before.
   - 4 weeks before.
   - 2 weeks before.
   - Final week.

4. Define evidence package.
   Include:
   - Problem statement.
   - Clinical rationale.
   - Pilot design.
   - Early data or demonstration.
   - Patient/community considerations.
   - Governance and consent.
   - Risks and limitations.
   - Next phase.

5. Define artifacts.
   Possible artifacts:
   - One-page executive memo.
   - Pilot protocol summary.
   - Consent/data governance note.
   - Slide deck.
   - Demo script.
   - Case vignette, de-identified.
   - Metrics table.
   - Partner roles map.
   - Public wording approved by institution.

6. Define claims ladder.
   Categorize statements:
   - Safe to say now.
   - Safe after pilot data.
   - Only as hypothesis.
   - Do not say.

7. Define approval path.
   Identify who must approve before external presentation.

## Output format

### Veredicto

State whether the project is conference-ready, near-ready, or not ready.

### Evento y ambigüedad

What is known, unknown, and must be confirmed.

### Objetivo de presentación

Pick one primary objective.

### Evidencia mínima requerida

Table:
Evidence | Needed for | Current status | Owner | Deadline

### Artifacts

Table:
Artifact | Purpose | Owner | Status | Deadline

### Claims ladder

Safe now / Safe after data / Hypothesis only / Do not say.

### Backward plan

Timeline from event date or assumed date.

### Próximo correo o reunión

Provide the exact ask needed to reduce ambiguity.

## Quality gates

Before finalizing, verify:
- The output does not assume the conference exists if not confirmed.
- Evidence is matched to claims.
- Institutional approvals are explicit.
- The plan avoids public overpromising.
- A minimal version can still be presented if evidence is early.
